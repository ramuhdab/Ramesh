# Module Build Log: 03 — Attachments, Data Import/Export, Reporting & Dashboard

**Status:** Shipped (v0.3) | **Date:** 2026-07-09

## Workflows covered
WF30 (Attachment Handling), WF34 (Data Import/Export), WF24 (Report Generation), WF25 (Dashboard Refresh).

## What was built
- **Attachments** (`modules/attachments`): generic upload/list/download/delete, linked to any entity by `(entityType, entityId)` so other modules (vendor documents, employee documents, damage-report photos) reference attachments by ID instead of reimplementing file handling. Sits on two swappable adapters: `lib/storage.adapter.ts` (local disk today; interface-compatible with a future S3/Azure Blob adapter) and `lib/virusScan.adapter.ts` (a stub that marks every file "clean" - a real scanner is an infrastructure decision documented in the deployment guides, not something this sandbox could install or test).
- **Data Import/Export** (`modules/dataio`): a generic bulk-import engine (`import.registry.ts` + `import.service.ts`) covering 8 modules — buildings, departments, positions, employee categories, inventory categories, employees, vendors, inventory items — parsing `.xlsx` (via ExcelJS) or `.csv` (via a small hand-rolled parser, `lib/csv.util.ts`), validating and coercing each row, and delegating actual row creation to each module's own service function (`employeeService.createEmployee`, `vendorService.createVendor`, `inventoryService.createItem`) rather than writing Prisma directly — so an imported row goes through the exact same business rules and cross-tenant checks as one created through the UI. A mirrored export engine (`export.registry.ts` + `export.service.ts`) dumps the same 8 modules to xlsx/csv/pdf.
- **Reporting & Dashboard** (`modules/reporting`): `GET /dashboard` (KPIs: employee counts, inventory alerts, pending procurement/indents, pending approvals for the caller's own roles, vendor status breakdown - every role gets one) and 5 predefined cross-module reports (inventory stock, employee issuance, procurement status, vendor performance, recovery/deductions) with a JSON preview endpoint and a PDF/Excel/CSV export endpoint.
- **Shared rendering utility** (`lib/tabularExport.ts`): renders `(columns, rows)` to xlsx (ExcelJS), csv (`csv.util.ts`), or pdf (PDFKit, hand-drawn table layout) - used by both the Data Import/Export module's export side and the Reporting module's report export, so this logic exists exactly once.
- Frontend: `Dashboard.tsx` now calls `GET /dashboard` on load and renders KPI cards (employees, inventory/stock alerts, procurement, my pending approvals, vendors) instead of the placeholder text from batch 1.
- New permission constants (`reporting:view`, `reporting:export`, `data:import`, `data:export`) - Attachments intentionally has no dedicated permission, matching `05-API-Specification.md` Section 14 ("authenticated" only).
- `docker-compose.yml`: added a named `spqr_uploads` volume so local-disk attachments/import data survive a container restart, and `STORAGE_PROVIDER`/`STORAGE_LOCAL_DIR` env vars on the backend service.

## Independent verification pass (LLM-as-judge)
A third fresh-context agent reviewed this batch the same way as the previous two (cross-tenant scoping, path-traversal defense, permission gating, multer/ExcelJS/PDFKit API correctness, error-handling consistency). It found **1 blocking issue, 4 moderate, and 5 minor**; all nine have been fixed:

**Blocking**
1. **Stored XSS via SVG upload.** The attachment MIME allowlist accepted a bare `image/` prefix, which matches `image/svg+xml` - and SVG can embed `<script>`. Combined with the download route serving files `Content-Disposition: inline`, opening a malicious SVG attachment would execute attacker JS. Fixed: the allowlist now only accepts explicit raster types (`image/png`, `image/jpeg`, `image/gif`, `image/webp`) plus PDF/Office/CSV/plain-text by prefix; the download route now only sets `inline` for a small explicit safe-render set (raster images + PDF) and forces `attachment` (forced download) for everything else, plus an `X-Content-Type-Options: nosniff` header.

**Moderate**
2. **`DELETE /attachments/:id` had no ownership or permission check** - any authenticated user in the organization could delete any other user's attachments. Fixed: restricted to the original uploader or an Organization Administrator (this endpoint isn't in the API spec at all - it's additive surface, kept deliberately conservative).
3. **Dead `isSuperAdmin` bypass parameter** in the attachment service - unreachable in practice because a Super Admin's JWT always has `organizationId: null` and the route layer rejects that before the service is ever called. Removed for consistency with how every other module handles organization scoping.
4. **No `MulterError` branch in the global error handler** - an oversized upload (both Attachments and Import cap at 10MB) surfaced as a generic 500 instead of a clear 400. Fixed.
5. **Corrupted/mistyped `.xlsx` uploads threw a raw ExcelJS exception** instead of a handled `AppError`, also surfacing as a 500. Fixed: `workbook.xlsx.load()` is now wrapped and rethrown as `AppError(400, "INVALID_FILE_FORMAT", ...)`.

**Minor**
6. Report date filters (`fromDate`/`toDate`) weren't validated before reaching Prisma - an unparseable date produced `Invalid Date` and a raw 500. Fixed: now validated with a clear `AppError(400, "INVALID_DATE_FILTER", ...)`.
7. The MIME-type check was skipped entirely when a file's mimetype was blank (`if (mimeType && ...)` fails open on missing input instead of failing closed). Fixed.
8. The report-export endpoint silently substituted a default format for any invalid value, while the data-export endpoint (correctly) rejected one with a 400 - inconsistent behavior between two very similar endpoints. Fixed: both now use the same zod-enum-with-default-and-reject pattern.
9. The hand-rolled CSV parser/serializer had two edge-case gaps: a stray quote mid-field (not at the start) would incorrectly enter quote-mode and swallow the rest of the row, and the serializer's quoting trigger didn't account for a bare `\r` inside a value (which could be misread as half of the `\r\n` row separator on re-import). Both fixed.
10. `storage.adapter.ts`'s path-traversal guard didn't explicitly reject an empty reference (`path.resolve(baseDir, "")` equals `baseDir` itself, which passes the traversal check and would attempt to read/delete the storage directory). Not reachable today (every `ref` is always a `crypto.randomUUID()` string we generated), but hardened anyway since the code's own comment says to treat `ref` as untrusted.

## Deviations from the original spec (flagged, not silently assumed)
1. **Import error reporting is inline, not a downloadable file.** `05-API-Specification.md` Section 13 says `POST /import/:module` "returns job + error report if any" - implemented as the row-level errors (`{row, message}[]`) directly in the JSON response body alongside the `ImportJob` record, rather than writing a separate error-report file and adding a fourth (undocumented) download endpoint. `ImportJob.errorReportRef` stays `null` for now; it remains on the model for a future "download as file" enhancement if imports grow large enough that scrolling a JSON array in the response stops being practical.
2. **Data Import/Export and Reporting are deliberately separate concerns**, even though both render tabular data to xlsx/csv/pdf (sharing `lib/tabularExport.ts`). Import/Export deals in raw, near-1:1 table dumps of 8 modules (so an operator can round-trip export → edit → import); Reporting deals in 5 curated, cross-module, join-and-filter views. They were kept as two registries (`dataio/export.registry.ts` vs `reporting/report.registry.ts`) rather than one, so a "report" never accidentally becomes a re-importable template and vice versa.
3. **A few endpoints exist beyond the documented minimum**: `GET /attachments` (list by entity), `DELETE /attachments/:id`, `GET /import/:module/jobs`, `GET /export/:module/jobs`, `GET /reports` (list report keys). None of these are in `05-API-Specification.md`; they were added because the documented set alone left no way to list an entity's existing attachments or check on a past import/export job from the UI. All were included in the judge review's permission-gating check.
4. **`STORAGE_PROVIDER=local` is a single-instance-topology default**, explicitly not durable across an ephemeral container redeploy - this is fine for the low-cost single-persistent-instance deployment the AWS/Azure guides describe (and is why `docker-compose.yml` now mounts a named volume for it locally), but production deployments that move to auto-scaling/ephemeral compute must switch to a real S3/Azure Blob adapter first. `StorageAdapter` is written as an interface specifically so that swap doesn't touch any calling code.
